# AGENTS.md

## Commands (run from repo root)

- Full test suite (no torch, GPU, or engine packages needed — verified on a bare dev box):
  `python -m pytest tts-engine-common/tests/ impl/tests/ tools/tests/`
- Single test: plain pytest, e.g. `python -m pytest impl/tests/test_server_omnivoice.py -k seed`
- After changing a server's request schema or engine constants, regenerate snapshots and review the diff:
  `python impl/tests/update_snapshots.py`
- `tts-engine-common` does **not** need to be installed for tests — its conftest (and `impl/tests/_bootstrap.py`) add `src/` to `sys.path`.
- No lint, typecheck, formatter, lockfile, CI, or pre-commit is configured. Don't go looking for it or invent one.
- Actually running a server requires the engine package + a GPU and downloads model weights from HuggingFace on first start. The test suite never does this.

## Layout

- `tts-engine-common/` — shared FastAPI + Pydantic package. Design constraint: **no torch, no engine deps** — it must stay importable and testable on any box (see `pyproject.toml` comment and `docs/01-server-generification.md` D7).
- `impl/` — fifteen standalone FastAPI server scripts, one per engine: `server_breezeBlue.py`, `server_chatterbox.py`, `server_omnivoice.py`, `server_qwen3TTS.py`, `server_qwen3TTS_mlx.py`, `server_fasterQwen3TTS.py`, `server_dotsTTS.py`, `server_indexTTS.py`, `server_luxTTS.py`, `server_voxcpm.py`, `server_ming3TTS.py`, `server_ming3TTS_moe.py`, `server_pocketTTS.py`, `server_audio8TTS.py`, `server_kittenTTS.py`. Run via `python impl/server_<name>.py` or uvicorn; env config is documented in each module's docstring.
- `impl/tests/` — GPU-free test suite + committed `/capabilities` snapshots (`snapshots/`).
- `tools/` — `speak.py`, a command-line testing tool for any engine server: stdlib-only (no torch, no engine deps, no need to install `tts-engine-common`), discovers engine parameters from `GET /capabilities`. GPU-free tests in `tools/tests/` (network and aplay stubbed). Spec: `docs/03-speak-script.md`. Also `serve.py`, the stdlib-only launcher for `envs/` (Python 3.11+ for `tomllib`): `python3 tools/serve.py <engine>` syncs the env's venv only when its inputs changed, then `os.execve`s the venv python on the server script named by `[tool.tts-serve] server` in the env's pyproject. `--host H` / `--port N` set `<env-prefix>_HOST` / `<env-prefix>_PORT` for the server only (all servers default to 0.0.0.0:7500). Tests: `tools/tests/test_serve.py` (fake repos in `tmp_path`; uv/subprocess/execv stubbed).
- `envs/` — optional per-engine uv projects (currently `envs/omnivoice/`, `envs/chatterbox/` and `envs/kittentts/`) that build a dedicated venv for one server from a sibling engine git checkout plus editable `tts-engine-common`: `python3 tools/serve.py <engine>`, or by hand `uv sync --project envs/<engine>` then `uv run --project envs/<engine> python impl/server_<name>.py`. Each env's pyproject must name its server in `[tool.tts-serve] server` and the server's `<PREFIX>_HOST`/`<PREFIX>_PORT` prefix in `env-prefix` (a test checks both, including that the script reads `<PREFIX>_HOST` and `<PREFIX>_PORT`). Virtual projects (`package = false`); the `.venv` and `uv.lock` are gitignored. Torch pins are `override-dependencies`, not constraints, because uv also applies the checkout's own `tool.uv.sources`. The test suite doesn't use these. Spec, including the checklist for adding one: `docs/04-engine-environments.md`.
- `docs/` — design docs; `01-server-generification.md` contains the binding decisions (D1–D7).

## Architecture facts that change how you work

- The Pydantic `SynthesisRequest` model is the single source of truth: `GET /capabilities` is **derived** from it at import time via `build_capabilities()` (decision D4). Change the model, then regenerate the snapshot — never hand-edit the capabilities doc or a snapshot to match.
- Request models use `extra="forbid"` deliberately (D5): unknown fields must fail loudly with 422. Don't "fix" that into `extra="ignore"`.
- Servers read env config at **import time** (module-level `os.getenv`). Tests pin env in `impl/tests/_bootstrap.py` *before* any server import — that file is shared by `conftest.py` and `update_snapshots.py`, so keep the pinned values in sync with the servers' documented defaults.
- Core request vocabulary: `text`, `audio_base64`, `reference_text`, `language`, `seed` (`CORE_FIELDS`). Core response: `audio_base64`, `sample_rate`, `seed`, `time_used`, `rtf` plus per-server extras (e.g. `fid`). `language` is *not* guaranteed core — check `/capabilities`.
- The `/health` core is shared the same way the response core is: `CoreHealthResponse` in `tts_engine_common.models` carries `status`/`serverType`/`model`/`device`/`version` (the `version` field defaults to the shared `RELEASE_VERSION`). Server health models subclass it and override/add only `serverType` (`Literal`) and the config-bound `model`/`device` — never hand-roll `HealthResponse` from `BaseModel` or re-declare `status`/`version` per server.
- The `language` contract (docs/02-language-handling.md): **two-letter lowercase codes** only; null/empty normalizes to `en` at the request boundary (shared helpers in `tts_engine_common.language` — reuse them, don't re-implement). Engines with a different internal format (Qwen3-TTS lowercase names, dots.tts uppercase codes) map codes at their own server; auto-detection is exposed as the special value `auto`. This is why `schema_version` is 2 — don't "fix" servers back to accepting names/free-form.
- Enum-based `language` fields must build their `Literal` via `canonical_language_literal()` (`tts_engine_common.language`), never a hand-rolled `Literal[tuple(...)]`: CPython hashes `Literal` by the **frozenset** of its args, so pydantic's core-schema cache conflates same-code-set Literals and the first-built model's schema wins for *all* of them — silently reordering another server's advertised `/capabilities` enum (this shipped once: the MoE Ming snapshot carried the 0.5b code order). The helper pins canonical order ('auto' first, then sorted codes); feed `build_capabilities`' `languages=` argument through the sibling `canonical_language_codes()` too, so the advertised enum and languages list agree by construction.
- Four distinct output rates: 24 kHz (Chatterbox, OmniVoice, Qwen3-TTS, Qwen3-TTS MLX, faster-qwen3-tts, Breeze TTS 2, Pocket TTS, KittenTTS 2), **48 kHz** (dots.tts, LuxTTS, VoxCPM), 22.05 kHz (IndexTTS), **44.1 kHz** (both Ming 3 TTS servers and Audio8 TTS). dots.tts auto-selects CUDA/CPU (no device env var); its snapshot's `device` field is machine-dependent and the test deliberately compares everything *except* `device`. LuxTTS does take a `LUX_TTS_DEVICE` env var and reports the *configured* device in capabilities (pinned in `_bootstrap.py`), so its snapshot's `device` is deterministic. Don't "fix" a device mismatch in either case. KittenTTS 2's `KITTENTTS_DEVICE` defaults to `auto`, and the server mirrors the engine's cuda/cpu pick (torch backend — no auto-MPS) into capabilities, so its test also compares everything *except* `device`.
- Two version numbers, deliberately independent (`tts_engine_common.core`): `RELEASE_VERSION` (str, e.g. `"1.5"`) is the tts-serve release line — the single constant every server reports as `version` in `/health` and carries in its `FastAPI(version=...)` metadata (the old per-server `version="0.x.y"` stamps are gone; don't reintroduce them). It is bumped at the *start* of each release cycle, in the same commit as the README changelog placeholder, and must match the README heading and the git tag (tags have no `v` prefix). `SCHEMA_VERSION` (int, currently 2) is the client-contract version, advertised only as `schema_version` in `/capabilities` and hard-gated by `speak.py` — bumped **only** on breaking contract changes (docs/01 §3.5), never for new engines or additive params. A third, unrelated number: the `tts-engine-common` package version (`pyproject.toml` / `__version__`, historically always 0.1.0) follows its own schedule and is *not* the release line. Never conflate the three. Full workflow: the `version-bump` skill (`.agents/skills/version-bump/SKILL.md`).

## Test gotchas

- `impl/tests/stubs/` provides import-only stand-ins for `torch`, `numpy`, `soundfile`, `loguru`, `transformers`, and each engine package. `transformers` is stubbed because Audio8 has no engine package at all — its model/processor code ships *inside the checkpoint* and is loaded through `AutoModel`/`AutoProcessor`, so that stub (not an `audio8_*` stub) is what stands in for the engine. The `soundfile` stub implements `info()` (real WAV headers) but `read()`/`write()` raise, so the Audio8 suite patches the decode step, and the one test that needs a real encode self-skips unless real NumPy — and with it libsndfile — is installed — it runs on a GPU box, which is where the codec can actually produce NaN. Stubs are appended to `sys.path` **last**, so real installed packages always win on a GPU box.
- The Ming 3 TTS servers import the MoE sampler defaults from the engine's `ming_tiny.task_protocol` (DRY: no hardcoded magic numbers), so the test stub `stubs/ming_tiny/task_protocol.py` must mirror the engine's `FORMAL_*` values *exactly* — if the vendor changes them, the server follows automatically but the stub (and the capabilities snapshot's `default` entries) must be regenerated to match. `stubs/ming_tts.py` is a single module, not a package — that mirrors the engine's real shape (`ming_tts.py` at the repo root).
- The stub `numpy` must satisfy pytest's own introspection (`isscalar`, `bool_`, `ndarray`, `asarray`). If a cross-suite run dies with `AttributeError: module 'numpy' has no attribute ...`, see the comment in `stubs/numpy/__init__.py`.
- Pydantic v2 lax mode coerces `"yes"`/`"true"`/`"1"` to booleans — boolean-rejection tests must use values that are *not* coercible.
- `impl/tests/test_language_contract.py` asserts the shared docs/02 language contract once across *all* servers (null/empty → `en`, 422 for garbage/uppercase/names/non-strings, `auto` per declaration, capabilities default, and the canonical sorted `/capabilities` enum order — derived from the doc itself, so a regenerated-but-contaminated snapshot can't pass it). A new server must be added to its `SERVERS` list; per-server suites keep only engine-specific language tests.
- `impl/tests/test_versioning_contract.py` asserts the versioning scheme once across *all* servers (`/health.version` and the FastAPI app metadata carry the shared `RELEASE_VERSION`; `/capabilities` carries only `schema_version` and must *not* leak the release line). A new server must be added to its `SERVER_MODULES` list — an unwired server fails there even if its own suite passes.
- The suite covers the HTTP surface (capabilities, health, validation, 400/422 pre-flight, and — for Qwen3-TTS MLX and Breeze TTS 2 — the no-audio-output 500 path (stubbed empty generator). Actual synthesis is **not** tested (it needs a real model + GPU); the `/synthesize` success path is exercised where a test installs a fake model: faster-qwen3-tts (`impl/tests/test_server_fasterQwen3TTS.py`) pins argument forwarding to `generate_voice_clone`, Breeze TTS 2 (`impl/tests/test_server_breezeBlue.py`) pins the request dict, template selection, guidance kwargs, and seed/request-id forwarding to the streaming runtime, and LuxTTS (`impl/tests/test_server_luxTTS.py`) pins the two "nothing to speak" pre-flights against a fake engine (zero text tokens ⇒ 422 that never reaches `encode_prompt` or `generate_speech`; empty prompt tokens ⇒ 400 after `encode_prompt`; a tokenizer that raises, a `prompt_tokens` the guard cannot iterate, or an encode dict that is not a dict ⇒ the request is handed to the engine anyway) plus the 200 path, pinning every tuning kwarg forwarded to `generate_speech`, the `prompt_duration`/`prompt_rms` forwarded to `encode_prompt`, that a lone **pad token (id 0)** is not read as "nothing to speak" (emptiness is a token *count*, never truthiness), that the 400 names the request's own `prompt_duration` window, and that the staged reference file is cleaned up on the 422 exit.

## Per-engine quirks

- **Chatterbox** — no `reference_text` field (deliberate; it conditions on audio only). Only the first 10 s of the reference are used. Output is PerTh-watermarked by the library. Must be installed from git (or `envs/chatterbox/`): PyPI `chatterbox-tts` 0.1.7 predates the v3 checkpoints and lacks `MULTILINGUAL_T3_MODELS`, which the server imports.
- **OmniVoice** — omitting `reference_text` triggers on-the-fly Whisper transcription; the first such request pays the ASR model load. References over 20 s are trimmed at the largest silence gap.
- **Qwen3-TTS** — `language` takes two-letter codes (`en`, `zh`) or `auto`; the server maps codes to the engine's lowercase *names* internally (`en` → `english`). Omitting `reference_text` transparently enables speaker-embedding-only mode.
- **faster-qwen3-tts** — CUDA-only fork of Qwen3-TTS (`FASTER_QWEN3TTS_DEVICE` must start with `cuda`; the engine has no CPU/MPS backend). `xvec_only` (default `true` — deliberately out of step with the engine's ICL library default; our testing found x-vector the more consistent voice for streaming, don't "fix" it back) is x-vector mode: `reference_text` is ignored and the voice is consistent across requests (the sentence-streaming mode); `xvec_only=false` is ICL mode, where `reference_text` is **required** (422 without it — do not add an automatic x-vector fallback) and the voice can vary between requests (fresh random seed per request by default). `language` takes two-letter codes or `auto`; the server maps codes to the engine's lowercase *names*. The engine caches the encoded voice prompt per (file path, transcript), so the temp prompt file is content-hashed (SHA-256) rather than UUID-named **and kept on disk** — per-request deletion would race with a concurrent request for the same clip still queued on the synthesis lock (staging happens before the lock is taken); wipe the staging directory to reclaim space. Synthesis is serialized with a lock: the engine replays captured CUDA graphs (static buffers, not re-entrant) and keeps a shared prompt cache.
- **Qwen3-TTS MLX** — Apple-Silicon/MLX backend using `mlx-audio`. ICL voice cloning only: `reference_text` is **required** (422 without it — do not add an implicit speaker-embedding fallback at the server boundary). `language` takes two-letter codes or `auto`; the server maps codes to the engine's lowercase names internally. `seed` is meaningful and is applied with `mx.random.seed()` before generation
- **dots.tts** — the runtime demands a file path for prompt audio, so the server writes a temp file; reference transcript is optional. `language` takes two-letter codes or `auto`; the server maps them to the engine's uppercase codes / `auto_detect` internally.
- **IndexTTS-2.5** — 22.05 kHz output. No `reference_text` field (conditions on audio alone; first 15 s hard cut). Reference clips are staged as content-hashed (SHA-256) temp files that are **kept** — the model caches conditioning per path; wipe the staging dir to reclaim space. Emotion via at most one of `emotion_audio_base64` / `emotion_vector` (8 components) / `emotion_text` (needs `INDEXTTS_USE_QWEN_EMO=1`). `language` restricted to the five advertised codes (anything else 422s); no `auto`. `seed` is best-effort (no engine seed parameter).
- **LuxTTS** — 48 kHz output. Imports as **`zipvoice`** (stub dir `stubs/zipvoice/`; the package is a git repo, not on PyPI). No `reference_text` field (deliberate; the engine *always* transcribes the reference with Whisper — openai/whisper-base on GPU, whisper-tiny on CPU — so every request pays the ASR cost; the ASR model loads once at startup). No `language` forwarding: the engine has no language parameter (tokenizer auto-detects en/zh per segment, other scripts dropped), so the server accepts any two-letter code but does not forward it, and capabilities advertise `languages: null` — the no-support case of docs/02. `seed` is meaningful (solver initial noise from the PyTorch RNG; seed via `seed_everything` inside the synthesis lock) — reproducibility is bit-exact on CPU and near-exact (~1e-7 differences) on CUDA because of non-deterministic GPU kernels; don't "fix" the docstrings to claim bit-exact GPU output. The runtime demands a file path for prompt audio; the reference is one-shot (no engine prompt cache), so the temp file is deleted per request. Synthesis is serialized with a lock: `generate_speech()` mutates the shared vocoder's `return_48k` flag in place. `t_shift` must be > 0 (the solver's timestep schedule degenerates at 0). Two pre-flight guards keep the engine's two "nothing to speak" crashes out of the client's face; both run **under `_synthesis_lock`** (the engine tokenizer normalizes text through a shared, stateful `inflect` engine, so neither can run beside a generation — a client's 422 arrives in queue order, after whatever is in flight), which is why `synthesize()` carries an `except HTTPException: raise` ahead of the catch-all 500 handler. `_check_text_is_speakable` asks the **engine's own tokenizer** and 422s when the text yields zero token ids — the tokenizer drops every character that is not an ASCII letter or a CJK ideograph, so `...`, `1234`, markdown fences, emoji and Cyrillic/Japanese/Korean/Greek text tokenize to nothing, the predicted output length collapses to (or below) the prompt length, and the vocoder aborts in its first Conv1d (`Calculated padded input size per channel: (6). Kernel size: (7)`) — a 500 that a sentence-streaming client hits routinely. `_check_reference_was_transcribed` 400s when Whisper found no `en`/`zh` speech in the clip (prompt-token count 0 → the duration prediction divides by zero → `upper bound and lower bound inconsistent with step sign`); the window it names is **`prompt_duration` (default 5 s), not the clip** — `process_audio` passes it straight to `librosa.load`, so a 10 s clip that opens with 6 s of silence is a 400, and the message must name the window the client can act on. That check is **necessary, not sufficient**: Whisper hallucinates text on silence/music (`"Thank you."`), so such a clip can pass and yield a 200 that is not the speaker — the 400 covers the *empty* transcript, the case that crashes. Both guards are **fail-open** (an engine shape surprise must not become a new 500 path) and measure emptiness by token **count**, never truthiness: token id 0 is the pad token `_`, so a truthiness test rejects speakable text. Never swap the tokenizer call for a regex: only the tokenizer also catches a lone `[laughs]` (full of letters, but a whole `[tag]` part is looked up as a single token ⇒ zero ids).
- **VoxCPM** — 48 kHz output (with dots.tts and LuxTTS). 2B-parameter tokenizer-free TTS with three modes: **voice design** (no reference audio; the voice is described in parentheses at the start of `text`), **controllable cloning** (reference audio only), and **ultimate cloning** (reference audio + `reference_text`; the server passes the clip as both prompt and reference audio, so the model treats the clip as a spoken prefix and continues from it). `reference_audio` is *optional* (unlike most engines — voice design needs no clip); `reference_text` **requires** `audio_base64` (a cross-field validator 422s without it — a transcript with no clip is a client error, not a mode switch; don't "fix" it into a silent voice-design fallback). Cloning needs a VoxCPM2 checkpoint: the engine rejects `reference_wav_path` on VoxCPM1 models, and VoxCPM1 outputs 16 kHz — the response `sample_rate` is read from the loaded model (`model.tts_model.sample_rate`), not a constant, so a 1.x checkpoint via `VOXCPM_MODEL` at least self-corrects in the response (the capabilities doc is derived at import time and still says 48000). No `language` forwarding: the engine has no language parameter (auto-detects from text, 30 languages), so the server accepts any well-formed two-letter code but does not forward it, and capabilities advertise `languages: null`. `seed` is meaningful: `seed_everything()` plus the engine's own `torch.manual_seed` inside the synthesis lock; the response echoes the engine's `last_successful_seed` (read under the same lock), not the requested seed — `retry_badcase` (default on) increments the seed across retries, so echoing the request's seed would be a lie; bit-exact on CPU, near-exact on CUDA. The ZipEnhancer denoiser is deliberately *not* exposed (`load_denoiser=False` is hard-coded — no env var, no request field; a parameter that can never work is worse than none). `VOXCPM_DEVICE` accepts the engine's full grammar (`auto`, `cpu`, `mps`, `cuda`, `cuda:<index>`): the import-time check validates the grammar, the engine checks availability at load; `VOXCPM_MPS_DTYPE` is import-time-validated to fail fast. The runtime demands a file path for reference audio, so the server writes a UUID-named temp file, deleted per request (one-shot engine, no path-keyed cache). Synthesis is serialized with a lock: KV caches are mutated in place, `torch.compile`d functions are not re-entrant, and `@torch.inference_mode()` contexts are thread-affine.
- **Breeze TTS 2** — CUDA-only (the streaming runtime hard-rejects non-CUDA devices; `BREEZEBLUE_DEVICE` must start with `cuda`). The engine is a plain git repo (no packaging), so the server imports its `breeze_infer`/`models` packages only when the repo root is on `PYTHONPATH` — run `PYTHONPATH=. python ../tts-serve/impl/server_breezeBlue.py` from the repo root; the server's guarded import converts the missing-package case into an actionable startup message. The checkpoint must be a *local directory*: the engine downloads the backbone/text tokenizer from HuggingFace but reads the bundled `audio_tokenizer/` subdirectory from disk, so `BREEZEBLUE_MODEL` should point at a `huggingface-cli download BreezeBlue/breeze-tts-2 --local-dir ...` result. Voice clone and voice direction only — the engine's voice-design mode is deliberately *not* exposed (client does not support it), so `audio_base64` **and** `reference_text` (the exact transcript) are both required; omitting either is a 422, not a mode switch. An optional `instruction` switches to voice direction (same speaker, steered delivery) and is stripped before the engine call; `cfg_scale` (default 1.0, README recommends 4) is the CFG strength (finite and > 0 — `+inf` is rejected by a validator, mirroring the engine CLI); a non-default value **requires** `instruction` (422 without it — the CFG branch only exists on the voice-direction template, so the engine would 500 the combination otherwise; don't "fix" it back into a silent clone-mode default). No `language` forwarding: the engine auto-detects English/Chinese from text, so capabilities advertise `languages: null` (docs/02 no-support case). `seed` is meaningful: the process RNG is re-seeded per request and the engine re-seeds PyTorch at the start of sampling; near-exact on CUDA (non-deterministic kernels), so don't promise bit-exact GPU output. The runtime demands a file path for reference audio and re-encodes each request (no path-keyed cache), so the temp file is deleted per request. Synthesis is serialized with a lock: the streaming runtime mutates shared KV/codec state in place and the engine's own API is single-request behind a lock. `BREEZEBLUE_FAST_ALL=1` enables the CUDA-graph fast path (one-time warmup from the engine repo's `configs/fast.json`, located relative to the `models` package; import-time check fails fast if it's missing; ~14.4 GiB vs ~7.7 GiB eager).
- **Ming 3 TTS (0.5b)** — 44.1 kHz output (the released checkpoint's audio-VAE rate; the response echoes the rate read from the loaded model, capabilities carries the constant). The engine is a bare git repo and `ming_tts` is a top-level *module*: the repo root must be on `PYTHONPATH`; the guarded import turns the missing-package case into an actionable `SystemExit`. Zero-shot cloning via the engine's `TTS` task; `reference_text` **optional** — omitting it transparently enables speaker-embedding-only mode (Qwen3-TTS precedent; an explicitly-provided null must not 500 in the field validator). `language` codes (`zh,en,ja,ko,de,fr,es`) are forwarded verbatim as `language_id` (no name mapping, unlike Qwen3-TTS) and there is **no `auto`** (no engine sentinel for these tasks). No seed parameter in `synthesize()` → the server calls `seed_everything()` inside the synthesis lock; but encoded prompts are cached **in memory** per staged-path: repeat requests with the same seed reproduce each other, while the cold *first* request for a clip is not reproducible by later ones (only a server restart re-coldens the cache — wiping the staging dir just reclaims disk; the live behavior was measured, don't "fix" the docs back to claiming a wiped dir makes the cache cold). Reference clips are staged as content-hashed (SHA-256) temp files that are **kept** (`cache_prompts=True` keyed by path; wipe the staging dir to reclaim space). Engine mutates `rope_deltas` + runs under `@torch.inference_mode()` → lock mandatory. Text normalization needs `pynini` → `MING3_TTS_TEXT_NORMALIZATION=0` skips it.
- **Ming 3 TTS (MoE)** — 44.1 kHz output, *enforced* by the engine's release-contract validation (it refuses any other rate). The 7.9B-total/1.3B-active MoE checkpoint the engine confusingly calls **"tiny"** (`ming_tiny` package) — separate server from the 0.5b because the two checkpoints pin conflicting dependencies (separate venvs; `requirements-tiny.txt`). ICL cloning only: `reference_text` **required** (422 without it — the `seed`/`multilingual` tasks have no transcript-free mode; don't add a speaker-embedding fallback). The engine task is selected from the language code (`en`/`zh` → `seed`, `ja`/`ko`/`de`/`fr`/`es` → `multilingual`) and the code goes through as `target_language`. Sampler defaults are imported from the engine's `ming_tiny.task_protocol` `FORMAL_*` constants — the test stub `stubs/ming_tiny/task_protocol.py` must mirror them exactly (currently cfg 2.0, steps 10, sigma 0.25, temp 0.0). `seed` is passed to `generate()` (the engine seeds the pipeline itself — no server-side re-seeding); the response carries an extra **`stopped`** flag (false = stop detector never fired, output may be truncated). One-shot engine (no path-keyed prompt cache): UUID temp clip file, deleted per request (even on failure — cleanup in `finally`). Synthesis is serialized with a lock (shared latent-history/KV buffers; process-wide seeding per request).

- **Pocket TTS** — CPU-only (no device env var; the engine does not officially support GPUs), 24 kHz. `audio_base64` is *optional*: the voice is the clip (zero-shot clone), else the preset named by `voice`, else the loaded language's default preset; clip + `voice` together 422 (cross-field validator — don't "fix" it into a silent precedence). Cloning needs the *gated* HuggingFace weights; without them the engine sets `has_voice_cloning = False`, the server still starts, presets work, and a clip request is a `400` (checked after the clip pre-flight, so bad input still reports its own error). No `reference_text` field (engine has no transcript input; sending one 422s). One process = one language via `POCKET_TTS_MODEL` (default `english`; the prefix before `_` picks the code, e.g. `french_24l` → `fr`); `language` is accepted (well-formed codes only) but not forwarded, and capabilities advertise `languages: null` (docs/02 no-support case, the LuxTTS precedent) — the loaded checkpoint shows up in the `model` label. `POCKET_TTS_CONFIG` loads a custom YAML (local path / https / hf:// — the offline path; mutually exclusive with an explicit `POCKET_TTS_MODEL`, 422-free startup fail-fast): the `model` label becomes `pocket-tts-custom-config`, preset `voice` requests 422 (precomputed states belong to the shipped language checkpoints), and the no-clip fallback is the engine's own alba-clip *URL* via `get_default_voice_for_language(language, config=...)` — it reaches HF on first use, so a local config is NOT fully offline without a clip; the test stub's `default_parameters` must keep mirroring the engine's `DEFAULT_VOICE_FOR_CUSTOM_MODEL`/fallback behavior exactly. `seed` is meaningful: `seed_everything()` before generation inside the synthesis lock; bit-reproducible on CPU. Conditioned voice states are cached (LRU of 8, SHA-256 of the clip / preset name) under the same lock — `generate_audio` is called with `copy_state=True` so a cached state is never mutated. The engine wants a file path for a clip, so it is staged as a temp file and deleted right after the state is built (the cache holds the state, not the file). Synthesis is serialized with a lock: `generate_audio()` is documented not thread-safe.
- **KittenTTS 2** — 24 kHz. 1.7B-parameter 1-bit speech LM (`kittenml` package, import `from kittenml import KittenTTS`; PyPI currently matches git). Two speaker sources: `voice` (the checkpoint's 115 built-in voices, default `Bruno` — validated at **runtime** against `model.available_voices`/`decode_presets`, 422 with a sample list; the table is checkpoint data, so *not* a capabilities enum) or `audio_base64` zero-shot cloning; the two together 422 (engine treats them as mutually exclusive — don't "fix" it into a silent precedence). With neither, the checkpoint's default voice speaks: `reference_audio` is optional in capabilities. `reference_text` optional — omitting it triggers an on-the-fly Whisper transcription that runs in **English mode** (pass the transcript for non-English clips); a transcript without a clip 422s (VoxCPM precedent). Clips are staged content-hashed (SHA-256) and **kept** — the engine caches encoded clip + speaker embedding per path; wipe the staging dir to reclaim space. Synthesis is serialized with a lock (the model mutates a shared pending-speaker-embedding between `generate()` calls). No `language` forwarding: the language is carried by the voice (non-English voices are named after their language), capabilities advertise `languages: null` (docs/02 no-support case). `seed` goes to the engine via `advanced={"seed": ...}`; bit-exact on CPU (verified live), near-exact on CUDA. Expression control lives inside `text` (`[emotion]`/`<event>`/`(((emphasis)))` tags — engine: early beta) plus `preset` (`stable`/`expressive`) and raw sampler knobs (`temperature`/`top_p`/`top_k`/`min_p`). The server is KittenTTS **2** only: the same constructor also loads legacy ONNX models with a different `generate()` API, so a non-KITTEN2 checkpoint fails fast at startup (`hasattr(model, "decode_presets")` guard). The engine's `vllm`/`mlx` backends are deliberately not exposed. Python backend is not speed-optimized: ~8 GB free VRAM for CUDA, ~6 GB RAM for CPU (measured RTF ~9 on a laptop CPU — fine for testing, not production).

- **Audio8 TTS (Realistic Air)** — 44.1 kHz output (the checkpoint's own `codec_sample_rate`; the response reads it from the loaded model). **No engine package exists**: the checkpoint ships its own `modeling_arktts.py` / `processing_arktts.py` and the server loads them via `AutoModel`/`AutoProcessor` + `trust_remote_code=True`, so the server imports no `audio8_*` module and the import-only stand-in is the `transformers` stub. Never "DRY" this by importing the engine repo's `audio8_tts_infer.py` CLI — that CLI keeps a prompt cache keyed by *text only*, which would hand a previous clip's voice to the next request carrying the same text. `reference_text` is required **with** `audio_base64` and rejected **without** it (the bundled processor raises `reference_text is required when a reference voice is provided`; the reverse half-pair is a 422 rather than a silently dropped client field — don't add an implicit fallback). Omitting both is legal and gives the checkpoint's own voice (its only non-cloning mode: no presets, no voice design). No `language` forwarding (the engine has no language parameter; 23 languages detected from the text — `th`/`zh`/`ja`/`fr`/`de`/`ar`/`hi` verified live on GPU), so capabilities advertise `languages: null`. The one shared `max_seq_len=2048` text+audio budget drives the reference window (2–20 s; one context position per `codec_frame_size=2048` clip samples ≈ 21.5/s) and the 1500-character text cap; clips are **never truncated** (unlike Chatterbox / IndexTTS / OmniVoice) because an over-long clip is an over-budget request, not a degraded one. That window is enforced on the **decoded** samples, with the container header only as a pre-flight (a header is a claim: header-vs-decode disagreement over 0.5 s is a 400) — which is why MP3 references without a `Xing`/`Info`/`VBRI` length table are refused outright: libsndfile then guesses the duration from the first frame's bitrate and stops at the guess (measured: a 40.05 s VBR MP3 read back as 6.73 s, and every downstream check passed on the fragment). The tokenized prompt is measured after the processor, so an over-budget prompt is an actionable 400 instead of the native `ValueError: Prompt length N must be smaller than 2048` (or a FlashAttention RuntimeError) surfacing as a 500. No temp files anywhere: the processor takes in-memory `(samples, rate)` — no staging dir, no path-keyed cache. `max_new_tokens` is a *frame* budget (default 1024 ≈ 47 s) and `retry_max_new_tokens` (default 2000) mirrors the CLI's single retry when the first pass never emitted end-of-speech; the response's extra **`finished`** flag is the truncation signal. Both budgets are clamped **server-side** to `max_seq_len - prompt_positions` before being handed to `generate()`, because the engine clamps silently (`min(max_new_tokens, max_seq_len - prompt_width)`) — the retry must compare *clamped* budgets, or a wide prompt makes the retry a silent no-op that doubles latency and returns the same length (don't "fix" that comparison back to the request fields). The same arithmetic 400s a prompt that leaves under `MIN_GENERATION_FRAMES` (256 ≈ 12 s) over: the engine answers those with a 200 whose audio is a single 46 ms frame and `finished=True` (measured: 1500 Devanagari chars + 19.4 s clip = 1897 of 2048 positions used → 0.0 s of audio; the same shape with 623 free gave 3.2 s of real speech). A wide prompt can also starve the model with room to spare (651 free → 0.05 s) — no server-side arithmetic predicts that, which is why the docs push the vendor's 150-character guidance and `finished` is a truncation flag, not a quality guarantee. The WAV encoder runs `np.nan_to_num` **before** `np.clip` — clip does nothing to NaN/inf and libsndfile writes them at digital full scale (`nan → -32768`, measured). `temperature` and `top_k` must be positive (the bundled `ArkttsLegacyTopKTopPLogitsProcessor` and `generate()` both raise on 0 → rejected at the boundary; `greedy` is the deterministic switch). `seed` is meaningful: `seed_everything()` plus a dedicated `torch.Generator` inside the lock; warm repeats of one request are byte-identical, but the *first* request in a fresh process differs from later ones with the same seed (kernel/backend selection settles — measured, don't "fix" the docs into promising full reproducibility); `greedy` ignores the seed entirely. Synthesis is serialized: `_setup_generation_caches` rewrites decode caches on the model instance and `decode_audio` lazily attaches the shared codec. CUDA by default: `AUDIO8_TTS_DEVICE` takes the CLI grammar (`auto`/`cpu`/`cuda`/`cuda:N`), `AUDIO8_TTS_DTYPE` must be `float32` on CPU (the engine's own rule); measured RTF 0.6–0.8 on an RTX 4070 (~6.4 GiB VRAM), 6.6 on CPU.

## Adding a new engine

Copy the existing pattern: `impl/server_<name>.py` (config + deps in the module docstring, `extra="forbid"` request model, capabilities derived at import) + `impl/tests/test_server_<name>.py` + a snapshot generated by `update_snapshots.py`. See `impl/README.md` for the current parameter table and `docs/00-project-overview.md` Goal 3 for the intended workflow. In OpenCode, the `new-tts-engine` skill (`.agents/skills/new-tts-engine/SKILL.md`, registered via `opencode.json` `skills.paths`) walks through the full workflow including the test stub.
